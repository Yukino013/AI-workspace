# 使用量与额度管理模块开发文档

> 项目：AI 开发者工作台（ai-prompt）  
> 日期：2026-10-15  
> 状态：已实现（后端计量内核 + 四类入口接入 + 前端页面），待测试与验收。  
> 默认每日额度已按确认结果定为 1,000,000 Token；本文档同时作为该模块的实现说明与验收依据。

## 1. 模块目标

让用户知道“我调用了多少次 AI、消耗了多少 Token、今天还能用多少”，并在后端限制每日用量，避免多个请求同时通过检查后超出预算。

本模块适合学习四项后端能力：

| 能力 | 在本项目中的实践 |
| --- | --- |
| 数据建模 | 保存调用流水、每日汇总和额度设置 |
| 数据聚合 | 按日期、模型、业务来源汇总调用次数和 Token |
| 业务校验 | 调用前检查额度，拒绝超额请求 |
| 并发与一致性 | 原子预占、事务、幂等结算、异常恢复 |

**第一版推荐把“账户剩余额度”定义为工作台内的每日 Token 可用额度。** 模型供应商账户的真实余额属于另一个集成需求，不能由本模块的 Token 数据直接推算。

用户可以自己调整的额度属于个人用量预算。将来开放公共注册、由站点承担 API 费用时，还需要由管理员控制的账户上限；用户不能通过提高个人预算来提高站点授权额度。该能力建议另立后续阶段。

## 3. 第一版范围

### 3.1 包含的功能

1. 今日概览：调用尝试次数、成功/失败/取消次数、输入 Token、输出 Token、已计入额度、预占额度、剩余额度。
2. 最近 7 天和 30 天趋势：按日展示次数和 Token，无数据日期补 0。
3. 模型与来源分布：来源为 Prompt、对话、代码工具、工作流步骤。
4. 调用明细：时间、来源、模型、状态、用量来源、Token、耗时；分页和筛选。
5. 每日额度设置：设置个人每日 Token 预算，保存后对后续请求立即生效。
6. 服务端拦截：所有实际 AI 调用都必须先预占，普通请求和流式请求规则相同。
7. 异常处理：覆盖并发、重复提交、取消、上游失败、缺失 usage、跨天和服务重启。

### 3.2 暂不包含的功能

- 查询供应商真实余额、充值、支付、套餐、账单和人民币计费。
- 管理员分配额度、团队共享额度、组织成本分摊。
- 模型差异价格折算、缓存优惠和供应商账单核对。
- 自定义时区、邮件通知、CSV 导出、复杂报表系统。
- Redis、消息队列等新的基础设施。

不同模型的 Token 单价可能不同。第一版的 Token 合计用于了解用量和限制个人预算，不表示模型费用相同。

## 4. 统计口径与默认规则

### 4.1 推荐默认值（待用户确认）

| 配置 | 建议值 | 说明 |
| --- | --- | --- |
| 每日 Token 预算 | 1,000,000 | 新用户/首次使用的默认预算；不是赠送供应商余额 |
| 可设置范围 | 1～10,000,000，整数 | 第一版不设置“无限额”或独立暂停开关 |
| 单次最大输出 | 默认 4,096 Token | 按模型适配器支持情况校验并传给上游 |
| 同时运行上限 | 每用户 3 次 AI 调用 | 由服务端控制，跨业务、跨日期共用 |
| 日期边界 | Asia/Shanghai 每日 00:00 | 时间戳以 UTC 保存，额度日按该时区计算 |
| 趋势范围 | 7 天 / 30 天 | 包含今天 |
| 请求总时限 | 建议 180 秒 | 普通请求和 SSE 均适用，最终值按模型体验确认 |
| 明细分页 | 默认 20，最多 100 条 | 服务端校验页码、筛选范围 |

1,000,000 是本模块已确认采用的默认值（`DEFAULT_DAILY_LIMIT`）。对外服务前应按费用承担方式重新确定默认预算和站点硬上限。

### 4.2 什么算一次调用

- 一次普通生成或一次流式生成：一个调用尝试。
- 多轮对话的每次发送：一个调用尝试；输入用量包含本轮实际发送的历史上下文和系统提示。
- 三步工作流实际执行三步：三个调用尝试。工作流本身不再额外增加一次。
- 工作流失败后重试：只统计重新向模型发送的步骤；沿用的已成功结果不再次统计。
- 点击“再次运行”：产生新尝试和新用量。
- 仅做参数校验、鉴权失败、额度不足：没有向模型发起尝试，不计调用次数。
- 预占成功但还未进入上游尝试：只计入预占，不增加调用次数。

“调用次数”准确标签使用“调用尝试次数”：应用写入准备发送状态与供应商接收之间无法形成一个跨系统事务，进程在这个间隙崩溃时无法绝对证明供应商是否接收。

### 4.3 Token 和额度的区别

```text
reportedTokens = 供应商完整返回的实际 Token 合计
estimatedChargedTokens = 缺少完整 usage 时，按保守规则计入的额度
consumedTokens = reportedTokens + estimatedChargedTokens
availableTokens = max(0, dailyTokenLimit - consumedTokens - reservedTokens)
overageTokens = max(0, consumedTokens - dailyTokenLimit)
```

- `reportedTokens` 用于展示“供应商报告 Token”；输入、输出明细只累计已知值。
- `estimatedChargedTokens` 单独标识为“估算扣额”，不能伪装成供应商实际计费。
- `reservedTokens` 是仍在处理的请求占用的额度，会在结算时释放并转入已消耗。
- `availableTokens` 是目前允许新请求使用的额度。
- 即使供应商实际用量超出预估，也必须完整记入，不能为了让剩余为 0 而截断实际值。

例如：每日预算 1,000,000，已消耗 200,000，两个请求合计预占 120,000，可用额度为 680,000。一个请求预占 60,000、实际使用 20,000，完成后释放这 60,000，并增加实际消耗 20,000。

输入估算、供应商隐藏开销和输出限制的具体语义可能有差异，因此这个方案能防止本地并发重复花费同一份预算，**不能承诺供应商金额或真实 Token 绝对不超支**。

### 4.4 日期与历史口径

- 在最终成功的预占事务内，按服务端当前时间计算并固定 `quotaDate`，例如 `2026-10-15`；事务跨越午夜也沿用其已固定的日期。
- 10 月 15 日 23:59 开始、10 月 16 日 00:01 完成的请求，仍结算到 10 月 15 日。
- 不需要零点清空计数；新日期创建新的每日汇总记录。
- 预算修改仅影响当前日后续预占和未来日期；历史日期保存当时最后生效的预算。
- 统计从模块启用时开始；页面显示 `trackingStartedAt`，避免误以为启用前没有使用。
- 第一版不回填旧业务记录，避免错误记录、重试和复制步骤导致重复统计。

## 5. 页面设计

侧边栏增加“使用量与额度”，路由建议 `/usage`，沿用现有登录保护。

```text
使用量与额度                     最近 7 天 / 最近 30 天    刷新
统计开始日期：2026-10-15          统计时区：Asia/Shanghai

[今日调用尝试] [供应商报告 Token] [生成中预占] [今日可用额度]

今日额度：已消耗 / 预占 / 可用
估算扣额存在时，显示其数量和解释

[每日次数与 Token 趋势]
[按模型统计]                    [按业务来源统计]

每日 Token 预算 [1000000] [保存]
说明：这是工作台个人预算；每日零点按北京时间进入新额度日。

调用明细：日期、来源、模型、状态筛选
时间 | 来源 | 模型 | 结果 | 输入/输出 | 计入额度 | 用量来源 | 耗时
```

交互规则：

- 页面加载时请求概览与明细；支持手动刷新，不为第一版增加常驻轮询。
- 当前页面发起的生成结束、取消或失败后，刷新相关额度状态。
- 其他标签页的用量可能稍有延迟；是否允许调用始终以后端预占结果为准。
- 保存额度成功后刷新概览。低于“已消耗 + 预占”的修改应被服务端拒绝。
- 设置为 0 或超出允许范围时给出校验提示；第一版不使用 0 表示无限额。
- 额度不足时显示“本次预计需要 X Token，目前可用 Y Token”，并提供额度页入口。
- 单次请求过大时提示缩短上下文或降低输出上限，不只提示等待第二天。
- 达到并发上限时提示等待已有请求结束。
- 供应商缺失 usage 时显示“估算扣额”，输入/输出未知项显示“未知”，不能显示成实际 0。
- 删除会话、Prompt、工作流或业务历史后，明细保留计量数据，原记录链接显示不可用。
- 移动端卡片换行，明细支持横向滚动或紧凑卡片，保留筛选和分页。

第一版使用现有 Element Plus 与项目样式。趋势优先复用项目已有图表能力；若无现成依赖，可先用简单柱状图，避免为该功能引入大型报表系统。

## 6. 后端架构与一致性选择

推荐保持 Express 分层，业务准备数据后进入统一计量服务，再调用现有 Adapter：

```text
登录用户请求
  → 鉴权 / Zod 校验 / 资源归属校验 / 构建完整 messages
  → MeteredAIService.prepare：估算、预占、建立流水
  → MeteredAIService.chat / stream：调用 AIService → Adapter
  → 记录最终用量并幂等结算
  → 保存/关联业务结果，返回数据或 SSE 结束事件
```

`prepare` 返回内部执行句柄；上游调用只能消费一个已预占且归属匹配的句柄。业务服务不得绕过该入口直接发起 AI 调用。用户、来源和资源引用由服务端生成，不能信任前端上传的 `userId`、Token 数或结算状态。

**推荐第一版使用 MongoDB 多文档事务。** 每次预占与结算涉及账户、每日汇总、请求流水，单独对其中一张表执行 `$inc` 无法保证三者一致。

数据库前提：

- MongoDB 必须支持事务，例如副本集；单机 standalone 不满足该方案要求。
- 当前 `.env.example` 仅有普通本地连接地址，不能据此确认当前 MongoDB 已启用副本集。
- 实现前先检查本地实例；开发环境可配置单节点副本集，无需购买服务器。单节点不提供生产高可用。
- 不支持事务时，开发阶段明确报告未满足前提，不能退化成“先查再扣”。
- 数据库事务只包含短时间读写，禁止把耗时的供应商网络请求放进事务。
- 事务使用适当的持久化确认；遇到可重试冲突按数据库驱动支持的方式有界重试。提交结果不明确时先核对流水，再决定后续动作。

若希望继续使用 standalone，应重新设计“单个权威文档内原子预占 + 可恢复派生流水”的方案。本草案不同时维护两套一致性实现。

## 7. 数据模型

建议新增三个集合，沿用项目 Mongoose 风格。所有 Token/计数必须为非负安全整数；校验单次用量和计数累加上界，异常数字不得直接参与扣额。

### 7.1 QuotaAccount：账户策略与当前并发

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| userId | string | 用户 ID，唯一索引 |
| dailyTokenLimit | number | 当前和未来日期的个人预算 |
| activeRequests | number | 跨日期的预占/运行中请求数量 |
| mutationVersion | number | 每次预占、结算、预算修改递增，串行化同一账户策略操作 |
| trackingStartedAt | Date | 计量启用时间 |
| createdAt / updatedAt | Date | 时间戳 |

并发上限为服务端配置，不能由普通用户在请求中指定。首次创建使用唯一索引配合 upsert，并处理首次并发初始化冲突。

### 7.2 DailyUsage：每天的权威额度汇总

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| userId + quotaDate | string + string | 联合唯一索引，日期为北京时间 `YYYY-MM-DD` |
| dailyTokenLimit | number | 该日最后生效的预算快照 |
| startedRequests | number | 已进入上游尝试的次数 |
| successRequests / failedRequests / cancelledRequests | number | 已结束的尝试结果数量 |
| reportedInputTokens / reportedOutputTokens | number | 已知输入、输出汇总，未知部分不填成 0 的事实 |
| reportedTokens | number | 具有完整 usage 的总 Token |
| estimatedChargedTokens | number | 没有完整 usage 的保守扣额总数 |
| consumedTokens | number | 完整实际用量与估算扣额的合计 |
| reservedTokens | number | 仍被请求占用的额度 |
| updatedAt | Date | 最后更新时间 |

正在进行的尝试不属于成功/失败/取消，不能要求三类结束数量始终等于 `startedRequests`。

### 7.3 UsageRequest：每次尝试的持久化流水

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| requestId | string | 服务端生成的内部流水 ID，唯一索引 |
| userId + operationKey | string + string | 同用户业务操作的幂等键，联合唯一索引 |
| payloadHash | string | 规范化业务入参摘要，检测同键不同请求 |
| quotaDate | string | 固定的额度归属日 |
| source | enum | `prompt / conversation / code_tool / workflow` |
| sourceRef | object | 业务对象、结果引用；工作流含 runId、stepId |
| model / provider | string | 服务端确定的模型和供应商标识 |
| status | enum | `reserved / running / settled` |
| outcome | enum / null | `success / error / cancelled / not_sent` |
| usageSource | enum / null | `reported / estimated / none` |
| estimatedInputTokens / maxOutputTokens | number | 本次预估输入和允许输出上限 |
| reservedTokens | number | 本次预占额 |
| reportedInputTokens / reportedOutputTokens / reportedTotalTokens | number / null | 供应商实际已知值，缺失为 null |
| chargedTokens | number / null | 结算扣额；结算前为 null |
| estimateVersion | string | 输入估算和保守扣额规则版本 |
| startedAt / finishedAt / deadlineAt | Date / null | 生命周期与恢复依据 |
| durationMs / errorCode | number / string | 耗时及归一化错误标识 |
| reconciledAt / reconciliationReason | Date / string | 恢复或修正记录 |
| createdAt / updatedAt | Date | 时间戳 |

辅助索引：`{ userId, quotaDate, createdAt }`、`{ status, deadlineAt }`。按模型/来源的索引根据查询量补充。

不保存 Prompt 正文、聊天内容、代码、API Key、Authorization 或上游完整错误响应。`payloadHash` 仅服务端使用、不对外返回；原始内容日志也不因本模块增加。

第一版不配置自动删除计量流水的 TTL。后续如归档流水，必须保留幂等与对账所需的数据，不能让删除影响额度或重复请求控制。

## 8. 预占、执行和结算

### 8.1 预占额度如何计算

```text
R = estimatedInputTokens + maxOutputTokens + safetyMargin
```

- 估算使用最终发送的完整 messages；多轮对话必须含实际上下文。
- 优先使用与模型匹配的 Token 计算能力，否则使用有版本的保守估算，并明确它不是精确计数。
- `safetyMargin` 用于消息包装等开销；具体系数需用实际模型响应校准，不能当成绝对上界。
- 输出上限必须真正传递到 Adapter，映射到当前模型支持的参数；不支持时返回明确错误，不能忽略。
- 校验模型上下文长度、输入大小及剩余额度；额度不足时第一版直接拒绝，不静默降低用户的输出上限。
- `R > dailyTokenLimit` 属于“单次请求预算过大”；`R > availableTokens` 属于“当日额度不足”。

### 8.2 预占事务

事务内执行：

1. 校验/创建 QuotaAccount，并通过实际递增 `mutationVersion` 参与该账户的写入竞争。
2. 根据 `userId + operationKey` 检查已有流水；相同业务请求返回已有状态，不再次预占；不同内容返回冲突。
3. 读取最新预算，确认 `activeRequests < 3`。
4. 找到/初始化当天 DailyUsage，以条件更新保证 `consumedTokens + reservedTokens + R <= dailyTokenLimit`。
5. 增加当日预占 `R`，增加账户 `activeRequests`，创建 `reserved` 流水。
6. 一起提交成功后才允许进入上游调用。

每次预算修改也必须写入同一 QuotaAccount，避免“读到旧预算后又在新预算下预占”的竞态。事务冲突重试时重新读取预算、日期和额度，不能重用旧判断。

同一账户的短事务会发生写竞争，这是第一版主动选择的简单一致性边界；不同账户互不共享这个锁点。

### 8.3 开始尝试与调用

预占提交后，短事务把 `reserved` 条件更新成 `running`，并增加当日 `startedRequests`。只有状态转换成功的执行者可以发起网络调用。

- 不能把“事务重试”写成重试整个 AI 网络调用。
- 流水写入失败或状态未能确认时不调用供应商。
- 普通请求与 SSE 都使用 AbortSignal、总时限和同一套结算逻辑。
- 不默认自动重试供应商请求。将来重试时，每个可能发送成功的尝试均须独立流水和预占。

### 8.4 幂等结算

事务内以 `requestId + 未结算状态` 为条件执行一次状态转换：

1. 将流水置为 `settled`，写入结果、用量来源和扣额。
2. 当日 `reservedTokens -= R`，`consumedTokens += chargedTokens`，同步实际/估算分类与结果计数。
3. 账户 `activeRequests -= 1`，递增版本。
4. 全部成功后提交。

重复 done、catch、finally、取消回调或恢复任务只能命中一次。已结算请求再次调用结算应返回已存在结果，不能重复扣额或再次减少并发。

额度流水与额度汇总必须在同一事务内。成功结果按可获得的 usage 结算；失败请求释放预占且不计入已消耗，仍保留失败流水供排查。

### 8.5 不同结束情况如何扣额

| 情况 | 计入额度 | 展示与处理 |
| --- | --- | --- |
| 成功，完整有效 usage | 供应商报告总 Token | `reported` |
| 成功但缺少完整 usage | 保守扣额 `max(R, 已知实际部分的下界)` | `estimated`；未知输入/输出显示“未知” |
| 失败，不论是否取得 usage | 0 | `error + none`，释放全部预占；保留失败流水与调用次数 |
| 确认没有进入上游尝试，例如预占后本地准备失败 | 0 | `not_sent + none`，释放预占；不增加调用次数 |
| 取消且取得完整 usage | 供应商报告总 Token | `reported`；取消不等同于失败 |
| 已进入上游尝试后取消，且缺少完整 usage | 保守扣额 `max(R, 已知实际部分的下界)` | `estimated`；未知输入/输出显示“未知” |
| 实际 usage 超出预占 | 完整实际用量 | 显示超出数量，并阻止后续超预算调用 |

缺失 usage 时输入/输出不能伪造为完整值。缓存、推理 Token 等额外分类由 Adapter 依据供应商协议解释；原始分类有重叠时不能直接相加。总 Token 的归一化规则需要测试，适配器不能把缺失字段默认成“已知为 0”。

成功但缺失 usage 时的估算扣额可能高于实际消耗。失败尝试不作估算扣额；即使供应商可能已处理请求，应用额度也按失败不计消耗处理。

### 8.6 重启、超时与恢复

- 所有请求设置明确总时限。恢复任务只处理超过 `deadlineAt + 恢复宽限` 的未结算流水。
- 仍为 `reserved`：通过条件状态转换回收；因为发送前必须先转成 `running`，可确认它没有获得发送资格。
- 已为 `running`：进程可能已经发送过；恢复为失败时释放预占并按零消耗结算，保留失败流水。
- 原执行进程与恢复任务竞争时，以流水的条件更新和事务决定唯一结算者。
- 多实例恢复任务使用相同幂等事务；单实例定时器不能承担一致性保证。
- 数据库不可用时拒绝新 AI 调用，保留现有错误提示；结算失败保留未完成流水并有限重试、报警，恢复后处理。
- 进程在收到实际 usage 后、落库前崩溃时，数据库可能只能恢复为估算。第一版不承诺恢复供应商账单精度。
- 并发计数可通过未结算流水核对。任何修复也必须与账户写入同步，不能在线无条件覆盖计数。

## 9. 幂等、对话与工作流的接入细节

### 9.1 前端重复提交

- 每次用户主动发起的新操作生成一个 UUID，随请求传递 `Idempotency-Key`；同次请求的网络重传复用原键。
- 服务端限定键长度/格式，唯一范围为当前用户；不接收客户端指定的内部 `requestId`。
- `payloadHash` 根据规范化业务入参、模型、输出上限、资源/版本引用计算；第一次冻结准备好的输入，重传不能因为会话已追加而重新计算成另一次生成。
- 同键不同参数返回冲突；同键仍运行返回已有状态，不启动第二条流。
- 同键已完成时返回已完成标识及可访问的结果引用；不重复生成。第一版不承诺自动重放旧 SSE。
- 用户明确点“重新生成/再次运行”时产生新键，新的真实调用正常计量。

必须在业务写入前识别重复操作，避免虽然没有重复扣额，却重复写入用户消息或创建工作流运行。

### 9.2 多轮对话

当前对话准备过程会先保存用户消息。接入后应调整为：

1. 校验归属，读取上下文，构建待发送消息但暂不写入用户消息。
2. 识别幂等操作，完成预占。
3. 将消息持久化并关联本次 requestId，再进入调用；持久化失败且尚未开始尝试时释放预占。
4. 上游失败时保留明确失败状态，重试不静默复制同一条用户消息。

第一版建议同一会话同时只允许一轮发送，避免多个请求读取不同上下文、回复顺序错乱；用服务端会话运行标识控制，并与请求恢复关联。它与“每用户最多 3 次调用”是不同约束。

### 9.3 工作流

- 额度粒度为“实际 AI 步骤”，每步在完整输入可确定后才预占。
- 不在工作流开始时一次预占所有步骤，因为后续输入包含前面步骤的输出。
- 步骤输入准备完后检查额度；中途不足时保留已完成输出，终止后续执行，展示“第 N 步额度不足”。
- 工作流 SSE 已开启后发生额度不足，发送带业务错误码的事件，并结束运行，不能尝试改写 HTTP 状态。
- 同一个 runId 的重复执行需要运行认领/状态条件更新，不能只检查一次 `status === running` 就允许多个执行器并发执行。
- 每个实际步骤使用稳定操作键，例如 `workflow:{runId}:{stepId}`；重试生成新 runId，复制的成功步骤跳过，失败及后续步骤重新计量。
- 运行认领必须有超时恢复；单纯在前端禁用“运行”按钮无法保证唯一执行。

## 10. HTTP 接口设计

所有接口放在 `/api/usage`，先执行现有 JWT 鉴权；服务端从 `req.user.userId` 确定用户。保持 `{ code, message, data }` 和现有 Zod/AppError 约定。

### 10.1 GET /api/usage/overview?days=7

`days` 仅接受 7 或 30。一次响应返回一致的今日汇总，以及按同一日期口径聚合的趋势和分布。

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "timezone": "Asia/Shanghai",
    "trackingStartedAt": "2026-10-15T02:00:00.000Z",
    "asOf": "2026-10-15T04:00:00.000Z",
    "today": {
      "quotaDate": "2026-10-15",
      "dailyTokenLimit": 1000000,
      "startedRequests": 12,
      "successRequests": 9,
      "failedRequests": 1,
      "cancelledRequests": 0,
      "activeRequests": 2,
      "reportedTokens": 180000,
      "estimatedChargedTokens": 20000,
      "consumedTokens": 200000,
      "reservedTokens": 120000,
      "availableTokens": 680000,
      "overageTokens": 0
    },
    "trend": [],
    "byModel": [],
    "bySource": []
  }
}
```

示例中的数组省略内容，不表示没有该功能。`trend` 每项包含日期、调用尝试数、实际报告 Token、估算扣额、合计消耗；分布使用相同指标。`activeRequests` 为账户当前跨日期值，今日次数不能用它直接相减得到今日已结束次数。

聚合规则：今日余额依据权威 DailyUsage，模型/来源按 UsageRequest 聚合；未结算请求不贡献已消耗 Token。历史输入/输出含不完整数据时带完整性提示。需要一致快照时用短只读事务；不将一次响应中的不同时点结果宣称为同一快照。

### 10.2 GET /api/usage/records

参数：`page`、`pageSize`、`startDate`、`endDate`、`source`、`model`、`outcome`。

- 日期按 `quotaDate` 筛选，单次范围最多 90 天，`startDate <= endDate`。
- 按 `createdAt DESC, _id DESC` 稳定排序，限制页码上界；后续数据量大时改游标分页。
- 返回 `{ items, total, page, pageSize }`。
- item 包含 requestId、时间、来源、允许访问的业务引用、模型、状态、结果、实际已知输入/输出、chargedTokens、reservedTokens、usageSource、durationMs、归一化错误码。
- 不返回用户密钥、消息正文、payloadHash 或上游完整错误内容。

### 10.3 PATCH /api/usage/quota

```json
{ "dailyTokenLimit": 1000000 }
```

验证范围为正整数且不超过服务端允许上限。事务内同时更新 QuotaAccount 与当前日 DailyUsage 的预算快照，并要求：

```text
newLimit >= today.consumedTokens + today.reservedTokens
```

允许提高预算；降低到低于已消耗与预占合计时返回明确错误；不取消正在生成的请求，不改变历史日期预算。成功返回最新预算和今日额度。

### 10.4 建议新增错误码

以下错误码为本模块提案，实现时核对全项目是否占用。

| HTTP | code | 含义 |
| --- | --- | --- |
| 400 | 40001 | 参数不合法，沿用现有约定 |
| 422 | 42201 | 单次预占超过整日预算，需调整输入/输出或预算 |
| 422 | 42202 | 新预算低于今日已消耗加预占 |
| 429 | 42901 | 今日可用额度不足 |
| 429 | 42902 | 同时运行数量已达上限 |
| 409 | 40901 | 相同操作正在运行或已经处理，返回安全的状态提示 |
| 409 | 40902 | 相同幂等键对应不同参数 |
| 409 | 40903 | 同一会话或工作流运行已被其他请求占用 |
| 503 | 50301 | 计量服务/数据库不可用，暂不接受新 AI 调用 |

沿用现有错误响应 `data: null`；所需数值通过安全的 `message` 展示。若以后需要结构化 quota 详情，应单独扩展统一错误契约，而不是假设现有 `fail()` 已支持。

### 10.5 SSE 响应规则

- 对单次生成，先完成归属校验、幂等识别与预占，再设置并刷新 SSE 响应头；预占失败直接返回 JSON 错误及相应 HTTP 状态。
- 预占后、开始流之前发生错误，同样确保释放或结算预占。
- 流开始后的异常用统一可识别的错误事件，例如 `{ "error": { "code": 42901, "message": "今日额度不足" } }`。
- 正常文本和 reasoning 事件保持现有兼容；必要时增加 `usage`/`quota` 元数据事件，所有对应前端解析器均应识别。
- 结算确认后才发送表示本次完整成功的结束标识。若结果已生成但结算待恢复，应明确提示统计处理中，不谎报扣额完成。

## 12. 验收与测试

| 场景 | 预期结果 |
| --- | --- |
| 四类业务正常调用，包括普通与流式 | 每次实际尝试只有一条计量流水，用量归属正确 |
| 余额不足/鉴权失败/输入不合法 | 不调用 Adapter；额度拒绝不增加调用次数，也不写入未发送用户消息 |
| 剩余 10,000，两个请求各预占 6,000 并发提交 | 最多一个通过，不会预占成 12,000 |
| 每用户并发上限为 3，同时提交 4 个请求 | 最多 3 个获得执行资格；不同用户隔离 |
| 同一幂等键双击、重传、多实例竞争 | 仅一次预占、一次上游尝试；业务消息也不重复 |
| 同键更换内容 | 返回冲突，不执行 |
| done 和取消回调同时触发 | 仅结算一次，预占和并发计数不为负 |
| 实际少于预占 | 消耗记实际，差额可重新使用 |
| 实际大于预占 | 完整记录实际并显示超出，不截断用量 |
| 取消/断流/成功但缺 usage | 标记估算扣额，未知值不冒充实际 0 |
| 预算修改和预占并发 | 使用事务序列中的最新有效策略，不发生旧预算绕过 |
| 请求跨午夜 | 结算原额度日，并发仍受账户级限制 |
| 工作流后续步骤不足、失败重试、重复执行 | 保留已完成输出；新步骤正常扣额，复用步骤不重复计量 |
| 同一会话同时发送 | 只接受一轮，避免上下文和回复顺序错乱 |
| 预占后崩溃、发送后崩溃、提交结果不明确 | 可根据流水恢复，不重复扣额，不盲目全退 |
| 数据库不可用 | 新调用不进入上游，待恢复流水保留 |
| 删除业务历史 | 汇总和额度不变 |
| 伪造其他 userId、读取他人流水、篡改 Token | 均不能改变计量或跨用户查询 |
| 空数据、估算数据、筛选、移动端、SSE JSON 错误 | 页面可理解，生成入口正确处理非 SSE 响应 |

测试分为：纯函数单元测试（日期、估算、usage 归一化）、真实副本集上的事务/并发集成测试、适配器模拟测试、前端构建与关键流程验证。事务测试不能仅用内存对象模拟来证明一致性；模拟模型响应，不为自动测试消耗真实供应商额度。

## 14. 开发前需要确定的取舍

建议先确认以下五项，再开始改业务代码：

1. **额度单位**：第一版用每日 Token 预算，供应商余额和人民币费用暂不纳入。
2. **预算默认值**：已定 1,000,000 Token/日、单次最多输出 4,096；可按个人使用情况调整。
3. **数据库方案**：接受使用 MongoDB 副本集事务，本地补齐环境；不要求现在部署公网。
4. **缺失 usage 的规则**：采用有提示的保守估算扣额，不把取消/断流一律当成零消耗。
5. **功能覆盖**：Prompt、对话、代码工具与工作流实际步骤全部纳入，同步补上幂等与恢复。

本方案主要复杂度在准确覆盖异常、并发和 SSE 生命周期；趋势图只是结果展示。如果希望先缩小版本，可以暂缓模型分布和趋势图，保留统一计量、预占、结算、恢复、今日概览及预算设置。

## 15. 参考与设计边界

数据库设计依据为 MongoDB 官方文档中的单文档原子性、多文档事务和事务部署要求。实施时应按本地 MongoDB/驱动版本核对 API 与事务配置：
